# vendors Supabase 장비 등록 검증 증거

- 검증 일시: 2026-08-14 15:07 KST
- 대상 프로젝트: `fhyozyktoqjudfvnajqe`
- 대상 코드: `vendors`
- 검증 범위: NDPS, 진인프라, TOBE DB 연동
- 비밀정보: 기록하지 않음

## 판정

**통과**

`vendors`는 Supabase `core` 스키마에 정상적으로 접근한다. NDPS와 진인프라의 등록 요청은 기존 `core.asset` UUID를 조회한 뒤 `core.vendor_device_mapping`에 업체 장비번호를 연결하고, 등록 토폴로지를 `core.vendor_topology_snapshot`에 저장한다. `DELIVER` 요청은 `core.vendor_integration_message`에 `PERSISTED` 상태로 저장된다.

단, 현재 `/register`가 하는 "장비 등록"은 신규 `core.asset` 생성이 아니다. `asset_code` 또는 `serial_number`가 이미 존재하는 자산만 업체 장비번호와 매핑한다. 미등록 장비의 UUID를 임의 생성하지 않는 동작도 함께 검증했다.

실행 명령:


원본 핵심 출력:

```text
[NDPS] mapped=200 unmapped=207 validate=ACCEPTED deliver=PERSISTED duplicate=IGNORED invalidMode=400 health=REACHABLE
[JININFRA] mapped=200 unmapped=207 validate=ACCEPTED deliver=PERSISTED duplicate=IGNORED invalidMode=400 health=REACHABLE

```

검증 의미:

| 항목 | 결과 | 의미 |
|---|---|---|
| Supabase 연결 | `REACHABLE` | 서버용 Supabase 클라이언트가 실제 프로젝트에 연결됨 |
| 기존 장비 등록 | `mapped=200` | 기존 자산 UUID를 찾아 업체 장비번호를 매핑함 |
| 미등록 장비 | `unmapped=207` | 일부 미매핑을 구분해 반환함 |
| UUID 자동 생성 방지 | `unmapped=NOT_CREATED` | 존재하지 않는 장비의 UUID/매핑을 임의 생성하지 않음 |
| 검증 전용 요청 | `validate=ACCEPTED` | 저장 없이 계약과 UUID 매핑을 검증함 |
| 운영 데이터 저장 | `deliver=PERSISTED` | 통합 메시지가 Supabase에 저장됨 |
| 중복 요청 | `duplicate=IGNORED` | Idempotency-Key 중복 저장을 방지함 |

## 4. 실제 등록 흐름

```text
NDPS/진인프라 POST /{vendor}/register
  -> 업체별 JSON 계약 검증
  -> TOBE lookupTobeDevices()
  -> core.vendor_device_mapping 조회
  -> 미매핑 번호를 core.asset.asset_code / serial_number에서 조회
  -> 기존 asset UUID가 있을 때만 vendor_device_mapping upsert
  -> vendor_topology_snapshot 저장
  -> 매핑/미매핑 결과 반환
```

## 5. 최종 결론

1. `vendors`의 Supabase 접근은 정상이다.
2. NDPS와 진인프라의 장비 등록 요청은 정상 처리된다.
3. 기존 자산 UUID와 업체 장비번호 매핑이 실제 DB에 존재한다.
4. 등록 토폴로지와 운영 메시지가 실제 DB에 저장된다.
5. 미등록 장비의 UUID를 서버가 임의 생성하지 않는다.
6. 신규 자산 자체를 만들려면 먼저 TOBE의 `core.asset` 등록 절차가 수행되어야 한다.
